MEASUREMENT METHOD

  the median "Duration" is reported.
- EXPLAIN ANALYZE used for actual rows processed per step
  ("rows scanned") and to locate the most expensive step.
- Times are machine-dependent; the relative comparison
  (OLTP vs star schema, same PC) is what matters.

QUESTION 1: Monthly Encounters by Specialty
------------------------------------------------------------

SQL Query:
SELECT DATE_FORMAT(e.encounter_date, '%Y-%m') AS encounter_month,
       s.specialty_name,
       e.encounter_type,
       COUNT(*)                     AS total_encounters,
       COUNT(DISTINCT e.patient_id) AS unique_patients
FROM encounters e
JOIN providers   p ON p.provider_id  = e.provider_id
JOIN specialties s ON s.specialty_id = p.specialty_id
GROUP BY encounter_month, s.specialty_name, e.encounter_type
ORDER BY encounter_month, s.specialty_name, e.encounter_type;

Schema Analysis:
- Tables joined: encounters, providers, specialties
- Number of joins: 2
- Specialty is not stored on encounters; it is reached through
  providers (encounters -> providers -> specialties).

Performance:
- Execution time: 0.438 seconds (median of 3 warm runs)
- EXPLAIN ANALYZE total: ~547 ms
- Estimated rows scanned: ~100,115 (8 specialties + 103 providers
  + 100,004 encounters), then 100,004 rows sorted for GROUP BY
- Result: 360 rows (24 months x 15 specialty/type combinations)

Bottleneck Identified:
1. JOIN chain: every one of the 100,004 encounters must be joined
   through providers to reach specialty_name (103 index-lookup
   loops into encounters).
2. GROUP BY on a computed value: DATE_FORMAT(encounter_date) is
   calculated for every row, so idx_encounter_date cannot be used
   (it only helps range filters; tested: filtering one month with
   a date range returned 15 rows much faster).
3. Full sort: all 100,004 joined rows are sorted in a temporary
   table before grouping; this is the most expensive step in
   EXPLAIN ANALYZE.
4. COUNT(DISTINCT patient_id) adds per-group de-duplication work.
Root cause: the attributes needed (month, specialty, type) live in
3 different tables and the month must be derived at query time, so
the whole encounter table is joined, transformed and sorted on
every run.

QUESTION 2: Top Diagnosis-Procedure Pairs
------------------------------------------------------------

SQL Query:
SELECT d.icd10_code,
       d.icd10_description,
       p.cpt_code,
       p.cpt_description,
       COUNT(DISTINCT ed.encounter_id) AS encounter_count
FROM encounter_diagnoses ed
JOIN encounter_procedures ep ON ep.encounter_id = ed.encounter_id
JOIN diagnoses  d ON d.diagnosis_id = ed.diagnosis_id
JOIN procedures p ON p.procedure_id = ep.procedure_id
GROUP BY d.icd10_code, d.icd10_description, p.cpt_code, p.cpt_description
ORDER BY encounter_count DESC, d.icd10_code, p.cpt_code
LIMIT 10;

Schema Analysis:
- Tables joined: encounter_diagnoses, encounter_procedures,
  diagnoses, procedures
- Number of joins: 3
- How diagnosis and procedure data are joined: the two junction
  tables have no direct link, so they are joined to each other on
  encounter_id. This pairs every diagnosis of an encounter with
  every procedure of the same encounter; diagnoses and procedures
  are then joined for the ICD-10 and CPT codes.

Performance:
- Execution time: 3.812 seconds (median of 3 warm runs)
- EXPLAIN ANALYZE total: ~3,907 ms (repeat run: 4,046 ms)
- Estimated rows scanned: ~900,000 row operations
  (149,598 procedure links + 373,894 diagnosis-link rows +
  373,894 diagnosis lookups), then 373,894 rows sorted
- Result: 300 distinct pairs; top 10 returned

Bottleneck Identified:
1. Row explosion: joining two junction tables on encounter_id
   multiplies rows (diagnoses x procedures per encounter).
   250,081 + 149,598 input rows became 373,894 joined rows
   (tested with SELECT COUNT(*) on the junction join).
2. Nested-loop index lookups: 149,598 lookups into
   encounter_diagnoses and 373,894 lookups into diagnoses.
3. GROUP BY sorts all 373,894 rows to produce only 300 groups;
   COUNT(DISTINCT) adds de-duplication work.
4. LIMIT 10 cannot short-cut the work: every group must be fully
   counted before the top 10 is known.
Root cause: many-to-many data stored in two separate junction
tables with no direct relationship, so pairing them requires a
row-multiplying join before aggregation.

QUESTION 3: 30-Day Readmission Rate
------------------------------------------------------------

SQL Query:
SELECT s.specialty_name,
       COUNT(DISTINCT i.encounter_id) AS inpatient_stays,
       COUNT(DISTINCT CASE WHEN r.encounter_id IS NOT NULL
                           THEN i.encounter_id END) AS readmitted_stays,
       ROUND(100 * COUNT(DISTINCT CASE WHEN r.encounter_id IS NOT NULL
                                       THEN i.encounter_id END)
                 / COUNT(DISTINCT i.encounter_id), 2) AS readmission_rate_pct
FROM encounters i
JOIN providers   p ON p.provider_id  = i.provider_id
JOIN specialties s ON s.specialty_id = p.specialty_id
LEFT JOIN encounters r
       ON  r.patient_id     = i.patient_id
       AND r.encounter_type = 'Inpatient'
       AND r.encounter_date >  i.discharge_date
       AND r.encounter_date <= i.discharge_date + INTERVAL 30 DAY
WHERE i.encounter_type = 'Inpatient'
GROUP BY s.specialty_name
ORDER BY readmission_rate_pct DESC;

Schema Analysis:
- Tables joined: encounters (i = index stay), encounters
  (r = readmission, SELF-JOIN), providers, specialties
- Number of joins: 3
- Readmission detection: for every Inpatient stay i, look for a
  row r of the SAME patient where r is Inpatient and
  i.discharge_date < r.encounter_date <= i.discharge_date + 30 days.
  LEFT JOIN keeps stays with no readmission; COUNT(DISTINCT CASE..)
  counts each readmitted stay once.
- Definition choice: "return" = another INPATIENT admission (standard
  hospital-quality definition). Counting ANY return visit would give
  ~32-34% instead of ~5-7%, mostly routine follow-ups.
- Result: Oncology has the highest rate (6.55%).

Performance:
- Execution time: 0.547 seconds (median of 3 warm runs)
- EXPLAIN ANALYZE total: ~640 ms ms
- Estimated rows scanned: ~266,000 (100,004 full scan of encounters
  for the Inpatient filter + ~166,000 rows from 15,074 patient_id
  index lookups x ~11 visits each in the self-join)

Bottleneck Identified:
1. Self-join on a large table: encounters is read twice; for each
   of 15,074 inpatient stays all of that patient's visits (~11) are
   fetched and range-tested; only ~0.06 rows per lookup survive.
2. No index on encounter_type: finding inpatient stays needs a full
   table scan (100,004 rows).
3. Specialty still needs the providers -> specialties join chain,
   plus 4 COUNT(DISTINCT) aggregations.
4. Risk: without the patient_id index (tested with EXPLAIN +
   IGNORE INDEX) the self-join becomes a full scan of ~100k rows per
   stay (~1.5 billion comparisons).
Root cause: readmission is a relationship between two rows of the
same table, which the OLTP schema does not store; it must be
recomputed at query time with a range self-join.

QUESTION 4: Revenue by Specialty & Month
------------------------------------------------------------

SQL Query:
SELECT DATE_FORMAT(e.encounter_date, '%Y-%m') AS service_month,
       s.specialty_name,
       COUNT(*)              AS claims,
       SUM(b.allowed_amount) AS total_allowed
FROM billing b
JOIN encounters  e ON e.encounter_id = b.encounter_id
JOIN providers   p ON p.provider_id  = e.provider_id
JOIN specialties s ON s.specialty_id = p.specialty_id
GROUP BY service_month, s.specialty_name
ORDER BY service_month, total_allowed DESC;

(Q4b ranking: same JOIN chain, GROUP BY s.specialty_name only,
 ORDER BY total_allowed DESC.)

Schema Analysis:
- JOIN chain: billing -> encounters -> providers -> specialties
- Tables joined: billing, encounters, providers, specialties
- Number of joins: 3
- Month = service month (encounter_date), consistent with Q1.
- Result: 192 rows (24 months x 8 specialties). Top revenue:
  Orthopedics ~$66.1M, then Emergency ~$51.0M. Specialty totals
  add up to SUM(billing.allowed_amount) = $299,654,156.71.

Performance:
- Execution time: 0.969 seconds (median of 3 warm runs:
  0.875, 0.969, 1.031)
- EXPLAIN ANALYZE total: ~1,062 ms
- Estimated rows scanned: ~200,000 row operations (8 specialties
  + 103 providers + 100,004 encounters + 100,004 index lookups
  into billing, 90,000 matched), then 90,000 rows aggregated in a
  temporary table

Bottleneck Identified:
1. Longest JOIN chain (3 joins): the measure (allowed_amount) is
   in billing but month and specialty live in 3 other tables.
2. The optimizer walks specialties -> providers -> encounters ->
   billing, doing 100,004 index lookups into billing; ~10% find no
   claim (wasted work).
3. Month derived per row with DATE_FORMAT, so no index can be used
   for grouping.
4. GROUP BY needs a temporary table over 90,000 joined rows.
5. Fragility: adding a junction table to the chain inflates revenue
   (tested: joining encounter_diagnoses gave $748.6M instead of
   $299.7M, 2.5x).
Root cause: facts (money) and the dimensions used to slice them
(time, specialty) are normalized into separate tables, so every
revenue query rebuilds the same 3-join path for every claim.

============================================================
SUMMARY - OLTP BASELINE (before star schema)
============================================================

Q  Question                          Tables Joins  Median   EXPLAIN
-- --------------------------------- ------ ----- -------- --------
1  Monthly encounters by specialty     3      2    0.438 s  ~500 ms
2  Top diagnosis-procedure pairs       4      3    3.812 s ~3,907 ms
3  30-day readmission rate             4*     3    0.547 s  ~640 ms
4  Revenue by specialty & month        4      3    0.969 s  ~1,062 ms
   (* encounters joined to itself)

Slowest: Q2 (row explosion from joining two junction tables).

COMMON ROOT CAUSES
1. Attributes needed together are spread across 3-4 normalized
   tables, so every query rebuilds the same JOIN chains
   (specialty is always 2 hops from encounters, 3 from billing).
2. Time grouping is computed per row (DATE_FORMAT), so the
   encounter_date index cannot help whole-period analysis.
3. Many-to-many data (diagnoses, procedures) multiplies rows when
   combined, and can double-count money if joined carelessly
   (revenue inflated 2.5x in a test).
4. Relationships between rows (readmissions) are not stored and
   must be rediscovered with a self-join on every run.
5. Large sorts/temporary tables for GROUP BY over 90k-374k rows.

=> These point directly to the star schema design in Part 3:
   pre-joined dimensions, a date dimension, one fact row per
   encounter with pre-aggregated counts/amounts, and bridge tables
   for diagnoses and procedures.
